<objective>
Persist a first-party Supabase `orders` record for every submitted frozen-drop checkout,
written **before** any payment-soliciting Square step, and re-source the Slack new-order
notification's line items from Square's order response instead of the legacy hardcoded
six-category label map (GitHub issue #9).

Purpose: Square's order object stops being the only record of an order. A row exists for
every attempted checkout — including ones where a Square call failed midway — so the
business has a durable audit trail and a table to hang a future payment webhook off.

Output: One additive migration, matching hand-edited generated types, a rewritten
persistence path in `app/api/checkout/route.ts`, and Vitest coverage for the new flow.
</objective>

- **No `currency` column.** `total_amount_cents integer` only; the USD assumption is
  documented in the migration header comment. CONTEXT explicitly permits this.
- **`integer`, not `bigint`**, matching the `int` style used elsewhere in the schema.
- **One migration**, `0008_order_status_totals.sql` — nothing is dropped, so no
  expand/contract split is needed.
- **`PRODUCT_NAME_LABELS` is deleted; `productName` stays.** `lib/cart.ts`
  (`isSauceBumpNeeded`) and `components/CheckoutClient.tsx` still produce and consume
  `productName`, and `cartSchema` must keep accepting it so it survives into
  `cart_snapshot`. Only the label map dies.
- **`lib/database.types.ts` is hand-edited in the same commit**, matching commit `1ca41db`
  from quick task `260904-uyl`. Regeneration against the live schema is a `<human-check>` step.
- **Insert failure is fatal (500); the two success updates and the failure-marking are
  best-effort and logged.** The insert runs before any Square call, so failing there costs
  the customer nothing. The later updates run after an invoice may already have been
  emailed — turning a bookkeeping write failure into a customer-visible checkout error
  would be strictly worse than a row stuck at `'pending'`.
- **The HTTP response body is unchanged.** `orderId` stays the Square order id;
  `/confirmation` and the e2e specs depend on it.
