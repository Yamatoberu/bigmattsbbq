<objective>
Fix the Square invoice due date so it reflects the customer's selected pickup/drop date instead of the day the order was placed.

Purpose: Customers currently receive an invoice that appears due immediately, which misrepresents the preorder model — payment is tied to a future frozen-drop pickup, not to checkout day. The pickup date is already fetched and unused for this purpose.

Output: One-line logic change in `app/api/checkout/route.ts` plus a regression test that locks the behavior in.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Supabase → checkout route | `drop_pickup_options.pickup_date` is operator-controlled data crossing into a Square API request body |
| checkout route → Square API | The invoice payload, including `due_date`, is sent to a third-party payment service |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-s0z-01 | Tampering | `pickup_date` value flowing into `payment_requests[].due_date` | mitigate | Column is a Postgres `date` type — Postgres itself enforces the `YYYY-MM-DD` shape, so no free-form string can reach Square's `due_date`. No client input is involved; the value is read server-side from the row already matched on both `id` and `drop_id`. |
| T-s0z-02 | Denial of Service | Invoice creation with a past `pickup_date` | accept | If an operator leaves a drop `active` past its pickup date, Square may reject the invoice and the checkout returns a 4xx instead of silently creating an order for a pickup that already happened. This is a louder and safer failure than the current behavior, affects only an already-broken data state, and fixing it belongs to drop lifecycle management, not this change. |
| T-s0z-03 | Information Disclosure | Test fixtures | mitigate | New test uses synthetic fixtures (`matt@example.com`, fake UUIDs, year-2099 dates) with all Square and Supabase calls mocked — no real credentials, no live API calls, no production data. |
| T-s0z-SC | Tampering | npm/pip/cargo installs | mitigate | Not applicable — this plan installs zero packages. Both files are edited with the existing dependency set; no `package.json` change. |
</threat_model>
