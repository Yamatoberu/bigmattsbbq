<objective>
Persist the customer's attribution answer against the Square order and surface it to Big Matt in Slack — without adding a single new way for checkout to fail.

Per 12-RESEARCH.md (verified against Square's canonical OpenAPI spec), the mechanism is the Order `metadata` map written inline in the `POST /v2/orders` body this route already sends. Not Order Custom Attributes (Beta end-to-end, requires a pre-created definition, cannot be set at CreateOrder time), and not a follow-up call.

Purpose: Square is the system of record for orders; this is the only durable store of the attribution answer. The Slack line is the only human-readable visibility channel, because application-written Square metadata is private to the writing application and does NOT appear in Big Matt's Seller Dashboard.
Output: extended `checkoutSchema`, `metadata` on the createOrder body, an enriched `notifySlackNewOrder`, and unit coverage for both.
</objective>

<square_metadata_constraints>
Square Order.metadata (verified against square/connect-api-specification api.json):
- Type: map<string,string>. Max 10 entries. Key max 60 chars, charset [a-zA-Z0-9_-].
  Value max 255 chars.
- Written inline in the CreateOrder request body — the SAME request that creates the
  order. A malformed value therefore 400s the whole checkout. All clamping happens in
  `buildAttributionMetadata()` (plan 01) BEFORE the value reaches this body.
- `metadata: undefined` in a JS object literal is safe: JSON.stringify drops undefined
  keys. This is the same behavior the existing `phone_number: customer.phone` line in
  the createCustomer body already relies on. No conditional spread is needed.
- Application-written metadata is PRIVATE to the writing application. It will not appear
  in the Square Seller Dashboard. Do not write any acceptance criterion phrased as
  "verify in the Square Dashboard".
</square_metadata_constraints>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `POST /api/checkout` | Untrusted `attributionSourceCode` / `attributionDetail` cross here into a payment-bearing flow |
| this app → Square `POST /v2/orders` | The attribution values become part of the same request that creates a real order |
| this app → Slack incoming webhook | Customer-supplied free text is echoed into a third-party message body |

| Threat ID | Category | Component | Disposition | Mitigation Plan |

No new class of data is exposed and no new recipient is introduced. Slack renders webhook `text` as markdown, not HTML, so there is no script-injection surface. |
| T-12-SC | Tampering | npm installs | accept | No new packages installed in this phase (12-RESEARCH.md "Package Legitimacy Audit: N/A"). |
