Create `docs/checkout-attribution.md`. Write it for a future maintainer picking up the deferred UTM / Meta campaign / email-campaign / first-touch work. Cover, in this order:

1. **What is stored and where.** The selected source's stable `code` is written to the Square Order's `metadata` map under key `attribution_source`, and the optional free-text detail under `attribution_detail`. Both ride inline in the same `POST /v2/orders` request that creates the order — there is no second call and no webhook. State that the choice list lives in Supabase `public.attribution_sources` and that Supabase stores no order data for this feature; Square remains the sole system of record for orders.

2. **Key naming convention and how to extend it.** State the `attribution_*` prefix as the reserved namespace for this concern. Record Square's hard limits: max 10 metadata entries per order, key max 60 chars restricted to `[a-zA-Z0-9_-]`, value max 255 chars. Note that 2 of the 10 slots are used, leaving 8 for future keys, and name the concrete candidates from the deferred list — `attribution_utm_source`, `attribution_utm_medium`, `attribution_utm_campaign`, `attribution_campaign_id`, `attribution_first_touch` — as the naming shape to follow. State explicitly that values must stay structured and separate: never concatenate source and detail into one string.

3. **Why Order `metadata` and not Order Custom Attributes.** Summarize the verified finding: every Order Custom Attributes operation is `x-release-status: BETA`, requires a one-time `CreateOrderCustomAttributeDefinition` setup call, and is keyed by `order_id` so it cannot be set inline at `CreateOrder` — it mandates a follow-up call after the order already exists. Note the counterweight: `Order.metadata` is itself tagged BETA at the field level (the `Order` object and the `CreateOrder` operation are PUBLIC), a risk accepted for this phase because the field has been present and documented for years. Include the re-verification trigger: re-check `x-release-status` on `Order.metadata` before any Square API version bump past the pinned `2026-04-21`.

4. **Visibility — read this before reporting a bug.** Application-written Square metadata is private to the writing application and does NOT appear in the Square Seller Dashboard order view. The two ways to see an attribution answer today are (a) the `Heard about us:` line in the Slack new-order notification, and (b) `npm run check:attribution -- <orderId>`, which calls `RetrieveOrder`. A future in-app reporting screen must read it back via `RetrieveOrder` / `SearchOrders` using this app's own access token.

5. **Reliability contract.** Attribution is best-effort and can never fail a checkout (D-10). Two independent layers enforce this: Zod bounds at `POST /api/checkout` (`attributionSourceCode` max 60 with charset `[a-zA-Z0-9_-]`, `attributionDetail` max 255) reject out-of-bounds input with a 400 before any Square call, and `buildAttributionMetadata()` in `lib/square.ts` independently trims and byte-truncates (UTF-8 byte length, not JS string length, so emoji/CJK detail text cannot slip past) and cannot throw. A Supabase failure loading the source list hides the question entirely rather than blocking the page (D-09). The submitted code is deliberately NOT cross-checked against live active Supabase rows — the list changes without a deploy, and a mismatch is a data-quality issue, not a correctness one.

   Then, still inside this section, add an explicitly headed subsection **Residual risk: D-10 holds by validation, not by call isolation**, written as prose a future maintainer can act on. It must make these points:
   - D-10 is phrased as "a failure to persist attribution (after order/payment otherwise succeeded) must not fail the checkout response." That phrasing presumes a *separable* persistence step that can fail on its own — the shape of the Slack notification, which is a genuinely separate, fire-and-forget `notifySlackNewOrder` call that can be `.catch()`-swallowed after the order already exists.
   - Attribution is NOT that shape. `attribution_source` / `attribution_detail` ride inline in the `metadata` map of the very same `POST /v2/orders` request that creates the order. There is no second call to isolate: if that request 400s because of a bad metadata value, no order is created at all. The failure mode D-10 literally describes cannot occur, and the failure mode that CAN occur (a bad value poisoning order creation) is worse than the one it describes.
   - Therefore the guarantee is delivered by making the value un-rejectable BEFORE the request is sent, not by isolating a call afterwards. Name the two layers concretely: (a) Zod bounds at `POST /api/checkout` reject out-of-range input with a 400 before Square is contacted at all, and (b) `buildAttributionMetadata()` in `lib/square.ts` independently trims, byte-truncates to Square's UTF-8 limits, type-guards non-string input, and contains no `throw` — so even if the Zod bounds and Square's real limits ever drift apart, the value placed in the order body is in-spec. State that these layers are deliberately redundant and that removing either one silently re-opens the risk.
   - State the accepted residual risk plainly: this is a *design* mitigation, not a *runtime* one. Nothing at runtime catches an attribution-caused `CreateOrder` rejection and retries without metadata. The residual risk is accepted because both layers are unit-tested (`tests/attributionMetadata.test.ts`, including multi-byte boundary cases) and because Square's limits for this field are documented and stable.
   - Record the re-verification trigger: if Square's metadata limits change, if `buildAttributionMetadata()` gains a code path that can throw, or if the Zod bounds are loosened, this tradeoff must be re-evaluated — and consider adding a runtime retry-without-metadata fallback at that point.
