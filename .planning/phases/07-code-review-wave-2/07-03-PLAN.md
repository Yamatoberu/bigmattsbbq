<objective>
Fix Issue 7 from `public/code_review.md` — `UNSUBSCRIBE_SECRET` falls back to
`BROADCAST_SECRET`.

Today, `lib/unsubscribeToken.ts:7` reads:

```
const secret = process.env.UNSUBSCRIBE_SECRET || process.env.BROADCAST_SECRET;
```

Coupling these two secrets means a forced rotation of `BROADCAST_SECRET` (e.g.,
after a credential leak) silently invalidates every outstanding unsubscribe link
emailed in the last 30 days. That is the worst possible UX for someone trying
to opt out — they would see "This link has expired" through no fault of their own.

The two secrets have fundamentally different rotation semantics:
- `BROADCAST_SECRET` gates the admin broadcast API; rotate freely.
- `UNSUBSCRIBE_SECRET` signs JWTs with a 30-day expiry; rotation
  invalidates all in-flight unsubscribe links.

Fix:
1. `getSecret()` reads ONLY `UNSUBSCRIBE_SECRET`. Throws if missing or `< 32` chars.
2. The thrown error explicitly says "Do NOT reuse BROADCAST_SECRET."
3. `.env.example` documents both secrets and notes they must be independent.

Purpose: Decouple two secrets with different rotation semantics; prevent
accidental link breakage on `BROADCAST_SECRET` rotation.
Output: Updated `lib/unsubscribeToken.ts` and `.env.example`.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-06 | Spoofing | Unsubscribe JWT signed with shared secret | mitigate | Decoupling means rotating `BROADCAST_SECRET` (e.g., after a leak) does NOT also invalidate every outstanding unsubscribe link. Each secret can be rotated on its own schedule, matching its risk profile. |
| T-07-07 | Tampering | Operator misconfiguration → reuse same value for both vars | mitigate | `.env.example` documentation explicitly says "Do NOT reuse one for the other"; the runtime error in `getSecret()` repeats the warning. Detection still relies on operator discipline — there is no programmatic check that the two values differ (out of scope: would require admin route to also load `UNSUBSCRIBE_SECRET` to compare). |
| T-07-08 | Information Disclosure | Error message reveals which env var is missing | accept | Error is thrown server-side and logged via `logError`; the message reaches operator logs but is not returned in HTTP responses (existing route handlers wrap errors in 500 + generic message). No customer-facing leakage. |
| T-07-09 | Denial of Service | Missing `UNSUBSCRIBE_SECRET` causes broadcast send to throw | accept | Same fail-loud behavior as before for missing secret; the operator must set the var. Removing the silent fallback is the intended, named improvement. |
</threat_model>
