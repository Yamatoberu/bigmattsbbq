<objective>
Fix Issue 12 from `public/code_review.md` — `useActiveDrop` polls every 30
seconds regardless of drop state.

Today, `components/hooks/useActiveDrop.ts:35-41` runs an unconditional
`setInterval(load, 30_000)`. Every browser tab that visits the site issues one
`/api/drop` request every 30 seconds for the entire session, regardless of
whether any drop is active. During the multi-week intervals between drops —
the majority of time — this generates steady background load on Supabase with
zero user-facing value.

Fix: stop polling once the drop is confirmed closed or absent. Restart polling
only if `state.drop?.status` changes back to a value where polling is useful
(i.e., `"active"`).

NOTE on NavBar double-polling: Both `OrderLanding` and `NavBar` independently
call `useActiveDrop()`, creating two parallel polling loops on every page load.
The fix to consolidate them (e.g., via context) is OUT OF SCOPE for this plan
— it would touch component boundaries and ship a different change. After this
plan ships, both polling loops will at least short-circuit when the drop is
inactive, mitigating the worst case (steady load between drops). The
consolidation is deferred to a future plan.

Purpose: Eliminate idle polling load on `/api/drop` and Supabase between drops.
Output: Updated `components/hooks/useActiveDrop.ts` with conditional interval
scheduling.
</objective>

<interfaces>
Current shape (`components/hooks/useActiveDrop.ts:35-41`):

```
useEffect(() => {
  void load();
  const id = setInterval(() => {
    void load();
  }, POLL_INTERVAL_MS);
  return () => clearInterval(id);
}, [load]);
```

This unconditionally schedules the interval on every mount, regardless of drop
state. It also uses `[load]` as the dep array; since `load` is wrapped in a
`useCallback` with empty deps, it has stable identity and the effect runs
exactly once on mount.

Target shape (per code_review.md Issue 12):

```
useEffect(() => {
  void load();
  const status = state.drop?.status;
  // Only poll while a drop might transition under us.
  // Stop polling when there is no drop, or when the drop is closed/inactive.
  const shouldPoll = state.drop !== null && status !== "closed" && status !== "inactive";
  if (!shouldPoll) {
    return;
  }
  const id = setInterval(() => {
    void load();
  }, POLL_INTERVAL_MS);
  return () => clearInterval(id);
}, [load, state.drop, state.drop?.status]);
```

Why include both `state.drop` and `state.drop?.status` in the deps:
- `state.drop` (object reference) covers null transitions: null → drop, drop → null.
- `state.drop?.status` covers status transitions on the same drop object: active → closed, etc.
- React's exhaustive-deps will not complain because both are explicitly listed.

DropDTO status field (from `lib/types.ts`):
- `"active"` — drop is open; poll for capacity changes / status flip to closed.
- `"closed"` — drop has ended; no further polling needed.
- `"inactive"` (or whatever the schema enumerates for "not yet open"): no UI consumption — out-of-window state.

Note: this hook's state machine treats `state.drop === null` (API returned no
drop) the same as a closed/inactive drop — no interval. The initial `void load()`
still runs on mount, so first-paint behavior is unchanged.

Behavior contract:
1. Initial mount: `void load()` runs immediately (unchanged from before — first-paint behavior is preserved).
2. After the first state update: the effect re-runs because `state.drop` and `state.drop?.status` changed from their initial values. On this re-run, `shouldPoll` is evaluated:

   - `status === "closed"` → return early; no interval.
   - `status === "inactive"` → return early; no interval.
   - Otherwise (typically `status === "active"`) → schedule the 30-second interval.
3. On unmount or status transition: the cleanup function (`return () => clearInterval(id)`) tears down any scheduled interval.

Notes:
- `state.drop?.status` is intentionally listed separately in the dep array even though `state.drop` already changes when the object reference changes. This is belt-and-suspenders for the case where the API returns a new object with the same status — exhaustive-deps will be satisfied.
- The early `return;` (without a cleanup function) is the correct pattern when `shouldPoll` is false: there is no interval to clear, so React doesn't need a cleanup. The previous render's cleanup, if any, has already run before this effect body executed.
- The conditional check uses string literals `"closed"` and `"inactive"`.
