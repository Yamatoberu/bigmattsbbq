Create `lib/sca/queries.ts` beginning with `import "server-only";` followed by a one-line comment noting it is importable only from Server Components and route handlers, exactly matching `lib/supabase-sca.ts:1-2`. Import `getScaSupabaseClient` from `../supabase-sca` and the view-model types from `./types`.

Export five functions:

1. `parseScaId(raw: string | string[] | undefined): number | null` — the input-validation control for both `[id]` routes. Return `null` unless the input is a single string that, after `.trim()`, matches `/^\d+$/`, parses to a value satisfying `Number.isSafeInteger`, and is strictly greater than `0`. Reject arrays, `undefined`, empty strings, `"1.5"`, `"-1"`, `"0"`, `"1e3"`, `" 12 "` is accepted only after trimming, `"abc"`, and `"1; DROP TABLE"`. Never coerce with a bare `Number()` without the regex gate — `Number("")` is `0` and `Number(" 12 ")` is `12`, so the regex is what actually rejects malformed input.

2. `getAllCooksWithScores(): Promise<CookWithScore[]>` — for the Dashboard. `.from("cook")` with the embedded select string `"id, steak_label, cooked_at, competition_id, competition:competition_id(id, name, event_date, city, state), score(*)"`, `.order("cooked_at", { ascending: true })`. Throw the raw Supabase `error` when present (the calling page catches it and logs it — never render it). Return `data ?? []`. Per D-07, apply no `chef_id` filter.

3. `getCompetitions(): Promise<ScaCompetitionRow[]>` — for the Competitions list. `.from("competition").select("*")` ordered by `event_date` DESCENDING (`{ ascending: false }`) so the most recent competition is first, matching COMP-01 and the UI-SPEC focal point "most recent competition's row card, positioned first". Throw on error; return `data ?? []`.

4. `getCompetitionWithCooks(id: number): Promise<CompetitionWithCooks | null>` — `.from("competition")` with select `"*, cook(id, steak_label, cooked_at, competition_id, competition:competition_id(id, name, event_date, city, state), score(*))"`, `.eq("id", id)`, `.single()`. When `error?.code === "PGRST116"`, return `null` (the caller turns that into `notFound()`); on any other error, throw it. This module owns the PGRST116 mapping so no page duplicates the error-code string.

5. `getCookWithDetails(id: number): Promise<CookWithDetails | null>` — `.from("cook")` with select `"*, competition:competition_id(*), score(*), cook_detail(*), cook_ai_review(*)"`, `.eq("id", id)`, `.single()`. Same PGRST116 → `null` mapping. `cook_ai_review` comes back as an array; normalize a null/undefined embed to `[]` before returning so the Cook Detail page can rely on `.length`.

Use the `Database["sca"]["Tables"][...]["Row"]` indexed-access types (via the aliases exported from `./types`) for return annotations — never the bare `Tables<>` helper (Phase 9 WR-04). Where the Supabase generic inference over an embedded select does not line up with the declared view model, cast the returned `data` through `as unknown as <ViewModel>` at the single return site rather than loosening the exported signature.

This module performs zero logging and zero user-facing error text — it throws or returns, and pages own the `logError` + generic-message presentation.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Public visitor → `[id]` route segment | The only untrusted input in the entire read-only tracker; arrives as an arbitrary URL path string |
| Node process → Supabase service-role client | Service-role key bypasses RLS by design (Phase 9 decision); the client must never reach browser JS |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-09 | Tampering | `parseScaId` / both `[id]` routes | mitigate | Regex-gated `/^\d+$/` + `Number.isSafeInteger` + `> 0` validation before any value reaches `.eq("id", ...)`; malformed input returns `null` so the page calls `notFound()` instead of issuing a query. Covered by explicit unit tests including a SQL-injection-shaped string. (ASVS V5 — the only V5-applicable surface in this phase per RESEARCH.md Security Domain.) |
| T-10-10 | Denial of Service | detail queries | mitigate | `.single()` PGRST116 is mapped to `null` inside this module rather than thrown, so a bad id produces a 404 instead of an unhandled SSR exception; every other error is thrown for the page's `try/catch` to log |
| T-10-11 | Information Disclosure | Supabase error objects | mitigate | This module never logs and never formats an error into user-facing text; it throws the raw error for the page to `logError()` server-side, keeping WR-02 (raw error rendered to visitors) structurally impossible here |
| T-10-12 | Elevation of Privilege | service-role client bundled into browser JS | mitigate | `import "server-only"` at the top of the file makes any client-component import a build-time failure, matching `lib/supabase-sca.ts` |
| T-10-13 | Information Disclosure (IDOR) | `/sca/competitions/[id]`, `/sca/cooks/[id]` | accept | Every `sca` row this milestone reads is public competition history for a single chef; there is no per-user data, no auth, and no ownership boundary to enforce (REQUIREMENTS.md: no auth this milestone; multi-chef support is deferred to PLAT-01). Enumerating ids exposes nothing a visitor cannot reach from the Competitions list. Revisit when PLAT-01 introduces multi-chef data. |
| T-10-SC | Tampering | npm installs | accept | No package-manager installs in this phase (RESEARCH.md Package Legitimacy Audit: not applicable) |
</threat_model>
