From lib/supabase.ts (the storefront client — DO NOT MODIFY THIS FILE):
```typescript
// Server-only singleton. Import only from API routes.
import { createClient, SupabaseClient } from "@supabase/supabase-js";
import type { Database } from "./database.types";

let _client: SupabaseClient<Database> | undefined;

export function getSupabaseClient(): SupabaseClient<Database> {
  if (_client) return _client;
  const url = process.env.SUPABASE_URL || process.env.NEXT_PUBLIC_SUPABASE_URL;
  const key = process.env.SUPABASE_SERVICE_ROLE_KEY;
  if (!url || !key) {
    throw new Error(
      "Missing Supabase environment variables. Check SUPABASE_URL (or NEXT_PUBLIC_SUPABASE_URL) and SUPABASE_SERVICE_ROLE_KEY."
    );
  }
  _client = createClient<Database>(url, key, {
    auth: { persistSession: false, autoRefreshToken: false, detectSessionInUrl: false }
  });
  return _client;
}
```

From lib/database.types.ts (top-level shape — the storefront type has ONLY a `public` key):
```typescript
export type Database = {
  __InternalSupabase: { PostgrestVersion: "14.1" }
  public: { Tables: { ... } }
}
```

Why a separate file is mandatory (not stylistic): supabase-js constrains `SupabaseClient<Db, SchemaName>`
to `SchemaName extends string & keyof Omit<Db, "__InternalSupabase">`. The storefront `Database` type has no
`sca` key, so `SupabaseClient<Database, "sca">` against it does not compile. A `--schema sca` generation
produces a `Database` whose top-level key is `sca`, which is what makes the generic type-check. This is
CONTEXT.md D-06 restated as a hard compile-time requirement.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server module -> browser bundle | The service-role key must never cross this boundary; crossing it exposes full RLS-bypassing database access |
| Next.js server -> Supabase PostgREST | Service-role credentials cross here on every SCA read |
| Supabase `sca` schema -> application | Data read here is rendered into public pages in Phases 10 and 11 |
