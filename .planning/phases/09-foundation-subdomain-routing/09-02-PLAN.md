## CRITICAL — the file is `proxy.ts`, NEVER `middleware.ts`

This repo pins `next: ^16.1.6` (installed 16.1.6). Next.js 16.0.0 deprecated the `middleware.ts` file
convention and renamed it to `proxy.ts`. Verified in the installed package: `next/dist/lib/constants.js`
defines `PROXY_FILENAME = 'proxy'`. Official Next.js 16 docs mandate:

- File at the **repo root**, same level as `app/` — `proxy.ts`
- Exported function named `proxy` (default export also accepted), signature `(request: NextRequest, event: NextFetchEvent)`
- Optional `export const config = { matcher: [...] }`
- Runtime defaults to Node.js; there is **no** `runtime` config option in this file — setting one throws

CONTEXT.md D-02 says "middleware.ts". That name is obsolete on this Next.js version. The rewrite semantics
D-02 describes are unchanged; only the file and function name differ. **Do not create `middleware.ts`.**

    Contents:
    - `import { NextResponse } from "next/server";` and `import type { NextRequest } from "next/server";`
    - `import { SCA_AREA_HEADER, resolveScaRouting } from "./lib/sca/routing";`
    - `export function proxy(request: NextRequest)` — the function MUST be named `proxy`.

    Function body, in this order:
    1. `const requestHeaders = new Headers(request.headers);`
    2. `requestHeaders.delete(SCA_AREA_HEADER);` — unconditionally strip any inbound value. This runs BEFORE any decision so a client cannot spoof `x-sca-area` (threat T-09-11).
    3. `const { isScaArea, rewritePathname } = resolveScaRouting(request.headers.get("host"), request.nextUrl.pathname);`
    4. `if (isScaArea) requestHeaders.set(SCA_AREA_HEADER, "1");`
    5. If `rewritePathname` is non-null: `const url = request.nextUrl.clone(); url.pathname = rewritePathname; return NextResponse.rewrite(url, { request: { headers: requestHeaders } });` Mutate only `pathname` — never `url.host`, `url.protocol`, or `url.origin`, so the rewrite can never become an open redirect or a cross-origin fetch.
    6. Otherwise: `return NextResponse.next({ request: { headers: requestHeaders } });`

    Also export the matcher config:
    `export const config = { matcher: ["/((?!api|_next/static|_next/image|favicon.ico|robots.txt|sitemap.xml|.*\\.(?:png|jpg|jpeg|gif|svg|ico|webp|avif)$).*)"] };`
    The leading `api` exclusion is deliberate: the SCA tree ships no API routes in this phase, and excluding `/api` keeps every existing storefront endpoint reachable on any host with zero behavior change (INFRA-03's "without changing existing routes").

    Do not add a `runtime` export or a `runtime` key in `config` — `proxy.ts` defaults to the Node.js runtime and Next.js 16 throws if a runtime is specified in this file. Add no comments beyond what is needed to explain the non-obvious header-strip ordering.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| internet client -> proxy.ts | Attacker-controlled `Host` and arbitrary request headers cross here before any app code runs |
| proxy.ts -> app/layout.tsx | The `x-sca-area` request header crosses here and drives a rendering decision |
| proxy.ts -> Next.js route resolution | The rewritten URL crosses here and selects which route module executes |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-11 | Spoofing | `x-sca-area` request header | mitigate | `proxy.ts` calls `requestHeaders.delete(SCA_AREA_HEADER)` unconditionally as its first action, before any branch, so a client-supplied value can never reach `app/layout.tsx`. Enforced by a line-ordering acceptance criterion. |
| T-09-12 | Tampering | rewrite target URL | mitigate | The rewrite clones `request.nextUrl` and mutates only `.pathname` with a `/sca`-prefixed string derived from the existing path. `host`, `hostname`, `protocol`, and `origin` are never assigned — enforced by a grep acceptance criterion — so the rewrite cannot be steered off-origin. |
| T-09-13 | Denial of Service | double-prefix 404 loop | mitigate | `resolveScaRouting` returns `rewritePathname: null` when the path is already under `/sca`, preventing `/sca/sca/...` (RESEARCH Pitfall 3). Covered by two explicit test cases. |
| T-09-14 | Spoofing | `Host` header on preview/unknown domains | accept | Vercel terminates TLS and binds the `Host` to a verified domain before the request reaches the app. A forged `Host: sca.*` on a non-sca domain only causes the SCA tracker to render, which is public read-only content in later phases — no privilege gain. |
| T-09-15 | Information Disclosure | storefront routes on the sca host | mitigate | `config.matcher` excludes `/api`, so storefront API endpoints keep their existing host-agnostic behavior and no new surface is created. All non-api paths on the sca host rewrite into `/sca`, which contains no storefront data. |
| T-09-SC | Tampering | npm/pip/cargo installs | mitigate | Not applicable — this plan installs no packages. `next`, `react`, and `@supabase/supabase-js` are pre-existing dependencies. |
</threat_model>
