## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| shell → npm registry | `npm install resend jose` fetches from registry; package-lock integrity hashes are the only defense against tampered tarballs |
| client retry → /api/checkout | A retried POST under flaky network conditions MUST NOT create duplicate Square customers/orders/invoices; idempotency key is the defense |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-5-07-01 | Tampering | npm package integrity on reinstall | mitigate | `npm install` (not `--no-save`, not manual edit) regenerates `package-lock.json` with SHA-512 integrity hashes per registry metadata; subsequent `npm ci` verifies hashes |
| T-5-07-02 | Repudiation / Duplication | Square order/invoice/customer creation on retried POST | mitigate | Deterministic SHA-256 key over (email, dropId, pickupOptionId, cart shape, purpose) — a retried identical request reuses the same key; Square deduplicates at the API layer |
| T-5-07-03 | Information Disclosure | Idempotency key contents | accept | Key is a hex SHA-256 digest — pre-image resistant; including `customer.email` in the pre-image is acceptable since the digest does not reveal it |
| T-5-07-04 | Tampering | Unbounded cart size in idempotency input array | accept | Zod schema caps cart via `.min(1)` and each `variationId:quantity` is short; SHA-256 is O(n) in input size with trivial absolute cost for typical carts (<50 items) |
</threat_model>
