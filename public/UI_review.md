## Issue 1 — ~~Mobile Hamburger Menu Not Visible~~ - DONE
**Severity:** 🔴 Critical
**Affected Pages:** All pages
**Viewport:** ≤ 959px (below the custom `nav` breakpoint)

### Problem
At mobile viewport widths (e.g. 390px), the desktop nav links correctly disappear but the hamburger/menu toggle button is also invisible. The mobile navigation DOM node exists (`<nav aria-label="Mobile primary">` inside a `<aside>`) and the trigger button exists (`<button aria-label="Open navigation menu">`), but neither is visible. Users cannot navigate to any page other than Home on mobile.

### Codebase Context (`components/NavBar.tsx`)
The project uses a **custom `nav` breakpoint at 960px** (`tailwind.config.ts` line 8 — `nav: "960px"`), not the standard Tailwind `md`/`lg`. All show/hide logic in `NavBar.tsx` uses this breakpoint:

- **Desktop nav** (line 53): `hidden nav:flex nav:flex-row nav:items-center nav:gap-8` — correct intent (hidden below 960px, flex at 960px+)
- **Hamburger button** (line 94): `inline-flex nav:hidden` — correct intent (shown below 960px, hidden at 960px+)
- **Overlay** (line 113): `nav:hidden fixed ...` — correct intent
- **Drawer** (line 124): `nav:hidden fixed ...` — correct intent

The JS toggle logic (`useState`, `onClick`, `aria-expanded`, `aria-controls`) is fully wired. The issue is almost certainly that **`nav:` prefixed utility classes are not being generated by Tailwind's JIT compiler**, causing the responsive overrides to silently disappear and leaving only the base class active.

### Root Cause
The `nav:hidden` class on the overlay and drawer means those elements are `display:none` at every width if `nav:` classes fail to generate. For the hamburger button, `inline-flex nav:hidden` would leave it visible — but if the *overlay/drawer* behind it has a `nav:hidden` that degrades to plain `hidden`, the whole mobile experience breaks.

Most likely cause: **Tailwind content path mismatch** — the `tailwind.config.ts` content globs may not be resolving to `components/NavBar.tsx`, so `nav:` classes never appear in the generated CSS.

### Diagnostic Steps
1. Run `npx tailwindcss -i ./app/globals.css -o /tmp/tw-out.css --minify` and grep for `nav\\:hidden` in the output. If absent, the breakpoint classes aren't generating.
2. Confirm `tailwind.config.ts` content array includes `"./components/**/*.tsx"` and `"./app/**/*.tsx"`.
3. In browser DevTools at 390px, inspect `<button aria-label="Open navigation menu">` — check computed `display` and whether any parent has `display:none`.

### Fix
1. **Verify content globs** in `tailwind.config.ts` cover `components/NavBar.tsx`. If `content` is missing the `components/` glob, add `"./components/**/*.{ts,tsx}"`.
2. **Confirm `nav` breakpoint** is under `theme.extend.screens` (not `theme.screens`, which would wipe Tailwind defaults) — it's at line 8, confirm the nesting.
3. If globs are correct and classes still don't generate, add the critical classes to the Tailwind `safelist`:
   ```js
   safelist: ["nav:flex", "nav:hidden", "inline-flex"]
   ```
4. After confirming classes generate, test the toggle at 390px, 430px, and 959px widths — both the button visibility and the drawer slide-in animation.
5. No changes to `NavBar.tsx` logic should be needed — the JS toggle code is correct.

## Issue 2 — ~~Nested `<main>` Elements (Invalid HTML)~~ - DONE
**Severity:** 🔴 Critical
**Affected Pages:** Home page (/)

### Problem
The accessibility tree on the homepage shows a `<main>` element (ref_17) that contains another `<main>` element (ref_18). Nesting `<main>` inside `<main>` is invalid HTML per the HTML5 spec. Screen readers announce the "main" landmark twice or behave unpredictably. Browser landmark navigation breaks.

### Root Cause (likely)
A global layout component (e.g. `Layout.tsx` or `_layout.tsx`) wraps content in `<main>`, and an individual page component (e.g. `index.tsx`) also renders its own `<main>`.

### Fix
1. Search for all `<main>` tags across the codebase.
2. Keep only one `<main>` per page. Typically, the page-level `<main>` is correct and the layout wrapper should use `<div>` instead.
3. Validate with an HTML validator or axe-core after the change.

```jsx
// Before (in Layout component — WRONG):
<main>{children}</main>

// After:
<div id="layout-wrapper">{children}</div>

// Keep <main> in the individual page component only
```

## Issue 3 — ~~Excessive Blank Whitespace at Bottom of Every Page~~ - DONE
**Severity:** 🟠 High
**Affected Pages:** All pages

### Problem
Every page has a large black empty section at the bottom (approximately 30–50% of the last viewport height) between the last content block and the footer. This makes the page appear broken or unfinished.

### Root Cause (confirmed)
**`app/layout.tsx:41`** — `<main className="flex-1">` is the culprit. The `body` uses `flex min-h-screen flex-col`, which is the standard sticky-footer pattern. `flex-1` on `main` causes it to expand and fill all vertical space between the `<NavBar>` and `<Footer>`. On any page where the content is shorter than the remaining viewport height, `main` grows silently and the dark background fills the void.

Severity by page (900px viewport assumed; navbar ~64px, footer ~72px → `main` height ≈ 764px):

| Page | Approx content height | Approx blank space |
|------|----------------------|--------------------|
| Contact | ~280px | ~480px (63%) |
| About | ~540px | ~224px (29%) |
| Home — no-drop state | ~200px | ~560px (73%) |
| Home — active drop | ~1400px+ | none (scrollable) |
| Catering | ~1200px+ | none |

No `min-h-screen` exists on any individual page section — the layout class on `main` is entirely responsible.

### Fix

**Step 1 — Remove `flex-1` from `main` in `app/layout.tsx`**

```diff
- <main className="flex-1">{children}</main>
+ <main>{children}</main>
```

With `flex-1` gone, `main` no longer grows to fill unused space. The footer follows the content directly. The body still has `min-h-screen flex-col`, so when total content is shorter than the viewport the body fills it — but nothing forces the footer to the bottom of the screen on short pages.

**Step 2 — Add bottom padding to genuinely short pages**

Without `flex-1`, the Contact and no-drop Home state pages will have their footer appear very high on the screen (content is only ~200–280px). Add intentional padding to the content containers so there's breathing room and the page doesn't look truncated:

- **`app/contact/page.tsx:10`** — `section` currently has `section-spacing mx-auto max-w-2xl`. Add `pb-24` (or increase to `py-20`):
  ```diff
  - <section className="section-spacing mx-auto max-w-2xl">
  + <section className="section-spacing mx-auto max-w-2xl pb-24">
  ```
- **`app/about/page.tsx:10`** — Same pattern, add `pb-20` to the outer section.
- **`components/OrderLanding.tsx:81`** — The no-drop state wrapper `<div className="bg-ember-radial bg-grain">` wraps only one section with `hero-content`. Add `pb-32` to the inner `<div className="hero-content ...">` or wrap it in a `min-h-[60vh]` container so it never looks empty.

**Step 3 — Verify `main`'s `relative overflow-hidden` from `globals.css:28`**

`main` currently has `relative overflow-hidden` from `globals.css`. After removing `flex-1`, confirm that removing it doesn't clip any decorative overflow effects (e.g., hero gradients that bleed outside their section). If any section uses negative margins or absolute-positioned decorations that extend beyond the section box, `overflow-hidden` on `main` was silently containing them. Visually check the home page hero and each section break after the change.

**No changes needed for:**
- Home (active drop) — content is long enough to fill the viewport naturally.
- Catering — same.
- Checkout, Confirmation — content is moderate; adding `pb-16` to the outermost container if needed.

### Expected result
Footer appears directly below content on all pages. Short pages (Contact, About) have intentional bottom padding so the footer isn't crammed against the content. The blank black void is eliminated.

## Issue 4 — ~~FAQ Accordion Has No Keyboard or ARIA Support~~ - DONE
**Severity:** 🟠 High
**Affected Pages:** Home (/), Catering (/catering)

### Problem
The FAQ items render with a ► toggle indicator but the trigger elements are plain `<div>` containers. The accessibility tree shows no `role="button"`, no `aria-expanded`, and no `aria-controls`. Keyboard users cannot discover or operate the accordion. Screen reader users receive no state change feedback.

**WCAG Failure:** 2.1 SC 4.1.2 (Name, Role, Value)

### Current State (verified 2026-05-02)
**The implementation already uses `<details>`/`<summary>` (Option A below)** — the review's diagnosis of plain `<div>` triggers was incorrect or based on stale state.

- `components/Faq.tsx` — renders the Home page FAQ using `<details>`/`<summary>`
- `app/catering/page.tsx` (lines 303–333) — inline `<details>`/`<summary>` for the catering FAQ

Native `<details>`/`<summary>` provides keyboard support (Tab to focus, Enter/Space to toggle) and screen reader disclosure-widget semantics automatically. No WCAG 4.1.2 violation exists in the current code.

### Remaining Work
The only open item is **visual polish** — the browser's default `▶` triangle marker on `<summary>` is currently unstyled. Whether this is intentional (using native browser affordance) or should be replaced with a custom chevron is a design decision.

**Option 1 — Keep default marker** (no code change needed): The browser-native triangle is familiar, accessible, and already there. Acceptable as-is.

**Option 2 — Replace with custom chevron** (minor CSS work):

1. In `app/globals.css`, suppress the default marker on all FAQ summaries:
   ```css
   details > summary {
     list-style: none;
   }
   details > summary::-webkit-details-marker {
     display: none;
   }
   ```
2. Add a CSS-only rotating chevron via a pseudo-element so the open/closed state remains visually clear:
   ```css
   details > summary::after {
     content: "›";
     float: right;
     transition: transform 0.2s ease;
   }
   details[open] > summary::after {
     transform: rotate(90deg);
   }
   ```
3. No changes to `Faq.tsx` or `catering/page.tsx` — purely a CSS layer.

### Fix — Option A (Recommended): Use Native `<details>`/`<summary>`
Replace the custom accordion with native HTML — zero JS required for basic functionality:

```html
<details>
  <summary>How do frozen drops work?</summary>
  <p>Order during the drop, choose your pickup window...</p>
</details>
```

Style `summary` to match the existing visual design and remove the default triangle with `list-style: none` / `::marker { display: none }`.

### Fix — Option B: Custom Accessible Accordion
If a custom implementation is required:

```jsx
<button
  aria-expanded={isOpen}
  aria-controls={`faq-answer-${id}`}
  onClick={() => setIsOpen(!isOpen)}
>
  {question}
</button>
<div
  id={`faq-answer-${id}`}
  role="region"
  aria-labelledby={`faq-trigger-${id}`}
  hidden={!isOpen}
>
  {answer}
</div>
```

Also add keyboard handler for Enter and Space keys if not using `<button>`.

## Issue 7 — ~~"Regular" Price Label Has Low Contrast and Zero Informational Value~~ - DONE
**Severity:** 🟡 Medium
**Affected Pages:** Home (/) — Individual Items section

### Problem
Each product card displays a muted grey "Regular" label above the price. This label:
1. Likely fails WCAG AA contrast ratio (4.5:1 minimum for normal text) against the dark card background.
2. Provides no useful information when every product shows the same label and there is no sale/compare price present.

Additionally, the "· 0 left" stock count is a child element *inside* the price element in the DOM, causing screen readers to read "Regular $16.00 · 0 left" as one run-on string.

### Fix
1. **Remove the "Regular" label** entirely unless a sale/original price is being displayed alongside it. If a compare-at price is added in the future, re-introduce the label then.
2. **Separate the stock count** into its own element with a clear accessible label:

```jsx
// Before:
<div>Regular</div>
<div>
  $16.00
  <span> · 0 left</span>
</div>

// After:
<p className="price">$16.00</p>
<p aria-live="polite">
  <span aria-label="0 items left in stock">0 left</span>
</p>
```

3. If the "Regular" label must stay, ensure its color meets a 4.5:1 contrast ratio. Use a tool like https://webaim.org/resources/contrastchecker/ to verify.
